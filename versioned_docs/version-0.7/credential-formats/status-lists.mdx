A [Token Status List](https://datatracker.ietf.org/doc/draft-ietf-oauth-status-list/) is a signed, compressed list with one status entry per credential, which the issuer publishes at a URL. Each credential points to its entry with the URL and an index, and the verifier fetches the list to check the entry. Credo uses status lists for [SD-JWT VC](./sd-jwt-vc.mdx) (as a JWT) and [mdoc](./mdoc.mdx) (as a CWT). This page covers creating and updating lists with `agent.tokenStatusList`, referencing them from credentials, and how verification checks them.

## What your app does

`agent.tokenStatusList` creates, updates and fetches status list tokens, and verification checks them. Everything around that is up to your app:

- Host each token at its URL, with content type `application/statuslist+jwt` or `application/statuslist+cwt`.
- Store the current token, and publish a new one after each change and before the current one expires.
- Allocate an index for each credential and remember which credential has which index. Pick unused indexes at random: indexes handed out in order reveal when a credential was issued.

The examples run an issuer, a holder and a verifier in one process, with a small HTTP server that stands in for your hosting:

## Create a status list

```ts showLineNumbers title="status-list.ts" format-status-list.ts section-2
```

- `format` is `jwt` for SD-JWT VC and `cwt` for mdoc.
- `statusList` sets the number of entries and the bits per entry (1, 2, 4 or 8). The statuses are 0 (valid), 1 (invalid) and 2 (suspended), so suspension needs at least 2 bits. Every entry starts at 0.
- `statusListUri` is the URL where you host the token. It becomes the `sub` claim, and verification fails when it doesn't match the URL in the credential.
- `signer` is `{ method: 'did', didUrl }` or `{ method: 'x5c', x5c }`, with a key in the agent's KMS. CWT lists need `x5c`.
- `expiresAt` and `timeToLive` set `exp` and `ttl`. `ttl` tells verifiers how long they may cache the list.

The result has the encoded token in `statusList` and the parsed token in `parsed`. Pass the format as type parameter, such as `createTokenStatusList<'jwt'>`, to get the matching result type.


- `status` takes one `{ index, status }` or an array, so you can change many entries in one update.
- The update keeps the URL, sets a new `iat`, and keeps `exp` and `ttl` unless you pass new values. Pass `expiresAt` again when the list should stay valid longer.
- `fetchTokenStatusList` downloads and parses a token, but doesn't verify its signature.

```ts showLineNumbers title="status-list.ts" format-status-list.ts section-6
```

- Any status other than 0 fails verification, including suspended.
- Pass `disableStatusValidation: true` to skip the check.
- Credo fetches the list on every verification, with the agent's `fetch`.

Which key may sign the status list depends on the [trusted issuer](../dids-and-trust/trust.mdx) that matched the credential:

- No trusted issuers configured (DID issuers only): the list must be signed with the credential issuer's key.
- A trusted DID: the list's `iss` must be that DID.
- A trusted X.509 issuer: the list's certificate chain must chain to the `status` certificates of the trusted issuer. Without `status`, it must chain to the `issuance` certificates and be the same chain that signed the credential.

### mdoc

mdoc status lists are CWTs signed with an X.509 certificate, and need an expiration time. Verification of an mdoc, and of a device response, checks the status the same way: any status other than valid fails.

As with SD-JWT VC, the status list must be signed by the same certificate chain as the mdoc, unless you trust a separate status list certificate with `trustedCertificates: [{ issuance: [...], status: [...] }]`.

## Other formats

- AnonCreds uses its own revocation registries, published on the ledger, and the holder proves non-revocation in the presentation. See [AnonCreds](./anoncreds.mdx).
- Credo doesn't check `credentialStatus` of W3C credentials. See [W3C Verifiable Credentials](./w3c-vc.mdx#status-and-revocation).
