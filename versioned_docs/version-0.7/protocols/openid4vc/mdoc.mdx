This page covers what is specific to mdoc (ISO/IEC 18013-5, `mso_mdoc`) in OpenID4VC, in the order of the flow. Issuance covers the issuer's credential configuration, certificate and signing, and the holder's trust and storage. Presentation covers the verifier's DCQL query and the result. [Issuing credentials](./issuer.mdx), [Receiving credentials](./receive.mdx), [Presenting credentials](./present.mdx) and [Verifying credentials](./verifier.mdx) explain the flow itself, and [mdoc](../../credential-formats/mdoc.mdx) explains the format.

Use mdoc for credentials that follow an ISO document type, such as the mobile driving licence, or that holders also present in person ([ISO mdoc](../mdoc/index.mdx)). To request mdocs from a website, see [Digital Credentials API](../dc-api/index.mdx).

## Issuance

### Configure the credential

Add an `mso_mdoc` entry to the `credentialConfigurationsSupported` of the issuer:

```ts showLineNumbers title="issuer.ts" openid4vc-mdoc.ts section-1
```

:::

- `doctype` is the document type, such as `org.iso.18013.5.1.mDL` for a mobile driving licence. Credo checks that every mdoc the mapper returns has this doctype.
- An mdoc is always bound to a key of the holder, never to a DID. `cose_key` (or `jwk`) in `cryptographic_binding_methods_supported` tells the wallet so.

In `credential_metadata.claims`, the `path` of a data element is its namespace and element identifier. Add a `scope` if you offer the credential through the [authorization code flow](./authorization.mdx).

:::

The subject must have a country (`countryName`): verification fails without it, and checks that `issuing_country` in the mdoc matches it (and `issuing_jurisdiction` the state, if present). In production, your issuing authority CA (IACA) issues the document signer certificate, and verifiers trust the IACA certificate. Pass the chain as an array, leaf first, to include it in the mdoc. [X.509 certificates](../../dids-and-trust/x509.mdx) explains creating certificates and chains.

### Sign the credential

The mapper returns the mdoc sign options, one entry for each holder key:

:::issuer

```ts showLineNumbers title="issuer.ts" openid4vc-mdoc.ts section-2
```

:::

- `docType` must be the `doctype` of the configuration, and `holderKey` is the key from `holderBinding`.
- `validityInfo` needs `validUntil`. Leave `signed` and `validFrom` out so they default to now: Credo rejects a `validFrom` that is even a few milliseconds before `signed`, which happens if you pass `new Date()`.
- `namespaces` maps each namespace to its data elements. Use `DateOnly` for elements of type `full-date`, such as `birth_date`. Every data element can be disclosed on its own.

For revocation, add `statusInfo` with a [status list](../../credential-formats/status-lists.mdx). `keyAuthorizations` lists data elements the wallet may sign itself (device signed).

The holder verifies the mdoc when it receives it, and the verifier verifies it again in the presentation. Both need the issuer certificate or its IACA root:

## Presentation

The verifier needs the same trust configuration as the holder, see [Trust the issuer](#trust-the-issuer).

### Request data elements with DCQL

The verifier asks for an mdoc by doctype and lists the data elements it needs:

:::verifier

```ts showLineNumbers title="verifier.ts" openid4vc-mdoc.ts section-6
```

:::

`format` is `mso_mdoc` and `meta.doctype_value` the doctype. Each claim `path` is a namespace and a data element identifier, and `intent_to_retain` tells the wallet whether you store the element. The wallet discloses only the requested data elements. Keep the default response mode `direct_post.jwt`: with OpenID4VP drafts 21 and 24, mdoc requests require it.
