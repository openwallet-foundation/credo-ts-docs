An SD-JWT VC ([IETF SD-JWT VC](https://datatracker.ietf.org/doc/draft-ietf-oauth-sd-jwt-vc/)) is a JWT signed by the issuer, in which the holder can disclose claims one by one. It's usually bound to a key the holder controls. This page covers `agent.sdJwtVc`: signing, storing, presenting and verifying SD-JWT VCs yourself. To issue and present them over OpenID4VC, see [SD-JWT VC with OpenID4VC](../protocols/openid4vc/sd-jwt-vc.mdx). The protocol calls these same APIs for you.

## Set up

Everything on this page is in `@credo-ts/core`. `SdJwtVcModule` is a default module, so every agent has `agent.sdJwtVc`. The agent needs storage and a KMS, here [Askar](../agent-setup/storage/askar.mdx). The examples use three agents: an issuer, a holder and a verifier.

## Sign a credential

The issuer signs with a key of a DID it created (or imported with its keys), and binds the credential to the holder's public key:

```ts showLineNumbers title="sd-jwt-vc.ts" format-sd-jwt-vc.ts section-2
```

- `payload` holds the claims. `vct` (the credential type) is required. Credo sets `iss`, `cnf` and `iat`; pass `iat: null` to leave `iat` out. Add `exp`, `nbf` or `status` yourself.
- `issuer` is `{ method: 'did', didUrl }` with a DID URL that points to a key, or `{ method: 'x5c', x5c }` with a certificate chain (see below).
- `holder` is `{ method: 'jwk', jwk }` (sets `cnf.jwk`) or `{ method: 'did', didUrl }` (sets `cnf.kid`). Without `holder` the credential isn't bound to a key, and anyone who has it can present it.
- `disclosureFrame` lists the selectively disclosable claims per object in `_sd`: property names, or positions for array elements. `_sd_decoy` adds fake digests so the number of claims doesn't leak. `iss`, `nbf`, `exp`, `cnf`, `vct` and `status` can't be selectively disclosable.
- `hashingAlgorithm` is the digest algorithm for disclosures: `sha-256` (default), `sha-384` or `sha-512`.
- `headerType` sets the `typ` header. The default is `dc+sd-jwt`. Use `vc+sd-jwt` only for verifiers that don't support `dc+sd-jwt` yet.

### Sign with an X.509 certificate

Put the certificate chain in `x5c`, leaf certificate first. Credo signs with the leaf certificate's key, so that key must be in the agent's KMS. A certificate you create with `agent.x509.createCertificate` from a KMS key is ready to use. For certificate chains and trust anchors, see [X.509 certificates](../dids-and-trust/x509.mdx).

## Store and query

The holder verifies a received credential, then stores it as an `SdJwtVcRecord`:

```ts showLineNumbers title="sd-jwt-vc.ts" format-sd-jwt-vc.ts section-4
```

- `kmsKeyId` is the KMS key the credential is bound to. Credo uses it to sign the key binding JWT when presenting. For a DID-bound credential, Credo finds the key through the DID instead.
- `credentialInstances` can hold several copies of the same credential, each bound to its own key. Issuers do this with batch issuance so the holder can present a fresh copy each time.
- Records are tagged with `vct`, `alg` and `sdAlg`, so you can query on them. `agent.sdJwtVc` also has `getById`, `getAll`, `update` and `deleteById`.
- `agent.sdJwtVc.fromCompact(compact)` decodes a credential without verifying it.

With OpenID4VCI, the holder flow returns the `SdJwtVcRecord` for you, with `kmsKeyId` set. You only store it.

## Present

The holder chooses which claims to disclose with a presentation frame, and adds a key binding JWT for the verifier:

```ts showLineNumbers title="sd-jwt-vc.ts" format-sd-jwt-vc.ts section-5
```

- `presentationFrame` sets `true` for each selectively disclosable claim to disclose, nested like the payload. Claims that aren't selectively disclosable are always included.
- `verifierMetadata` creates the key binding JWT with the verifier's `audience` and `nonce`. It fails for a credential without `cnf`. Leave it out to present without key binding.
- `additionalPayload` adds claims to the key binding JWT.

Pass `record.firstCredential` rather than the compact string, so Credo knows which key to sign with. For records with several instances, `useInstanceFromCredentialRecord` from `@credo-ts/core` picks an unused one.

## Verify

```ts showLineNumbers title="sd-jwt-vc.ts" format-sd-jwt-vc.ts section-6
```

`verify` returns `{ isValid: true, sdJwtVc }` or `{ isValid: false, error }`. `sdJwtVc.prettyClaims` holds the disclosed claims. It checks the issuer signature, the digests of the disclosures, `iat`, `nbf` and `exp` (with the agent's `validitySkewSeconds`), the `typ` header and the status. Options:

| Option | Effect |
| --- | --- |
| `keyBinding` | Requires a key binding JWT signed by the `cnf` key, with this `audience` and `nonce`. |
| `requiredClaimKeys` | Claims that must be disclosed, as dot paths such as `address.locality`. |
| `trustedIssuers` | The issuers to accept for this call. |
| `fetchTypeMetadata` | Resolves the type metadata of the `vct` into `sdJwtVc.typeMetadata`. A failed fetch doesn't fail verification. |
| `disableStatusValidation` | Skips the status check. |
| `now` | The time to verify against. |

Trust depends on how the credential is signed:

- DID: any issuer DID is accepted unless `trustedIssuers` or the agent's `getTrustedIssuersForVerification` callback returns a list. With a list, the issuer DID must be on it.
- X.509: verification fails unless a trust anchor is configured, per call or on the agent.

```ts showLineNumbers title="sd-jwt-vc.ts" format-sd-jwt-vc.ts section-8
```

To configure trust once for all verifications, see [Trusted issuers](../dids-and-trust/trust.mdx).

If the credential has a `status` claim, `verify` fetches the status list and fails when the credential is revoked or suspended. See [Status lists](./status-lists.mdx).

### Errors

Many errors from the SD-JWT checks have a `code`, so you can handle them without parsing the message:

```ts showLineNumbers title="sd-jwt-vc.ts" format-sd-jwt-vc.ts section-9
```

Common codes are `JWT_EXPIRED`, `JWT_NOT_YET_VALID`, `INVALID_JWT_SIGNATURE` and `STATUS_INVALID`. Time and status errors also have `details` with the values that were compared. Not every error has a code: checks that Credo does itself, such as issuer trust and the key binding audience, and some library checks, such as a missing required claim, only have a message.

## Type metadata and module options

SD-JWT VC type metadata describes a `vct`: display names, claim labels and rendering. By default Credo only resolves `vct` values that are HTTPS URLs, by fetching them. To serve type metadata yourself, or resolve other `vct` values, register `SdJwtVcModule` with a `customTypeMetadataResolver`:

```ts showLineNumbers title="sd-jwt-vc.ts" format-sd-jwt-vc.ts section-7
```

- `customTypeMetadataResolver` is called for the `vct`, and for each `extends` value in the type metadata. Return the type metadata document, `undefined` for none, or call `defaultResolver` for the HTTPS fetch. If the credential has a `vct#integrity` claim, your resolver has to check it; `IntegrityVerifier` from `@credo-ts/core` does that. The default resolver checks integrity itself.
- `customStatusListFetcher` replaces the HTTP request for the status list JWT, for example to allow only certain hosts or to cache lists. Credo verifies the returned JWT as usual.

Pass the module under the `sdJwtVc` key, which replaces the default module. `agent.sdJwtVc.fetchTypeMetadata(sdJwtVc)` resolves type metadata outside of verification.
