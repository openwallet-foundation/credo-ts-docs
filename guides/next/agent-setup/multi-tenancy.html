Multi-tenancy

With @credo-ts/tenants, one agent hosts many tenants. Each tenant has its own storage, keys, DIDs and credentials, while all tenants share the agent's modules, configuration and endpoints.

When to use tenants​

Use tenants for a service that issues, verifies or holds credentials on behalf of many organizations or users, such as an issuance platform or a cloud wallet. The alternative, an agent per customer, needs a process, a database and endpoints for each of them.

You don't need tenants for a mobile wallet, which has one user. You don't need them either to run several issuers or verifiers for one organization: one agent can host many OpenID4VC issuers and verifiers. Use tenants when each of them needs keys, DIDs and data of its own.

Install​

  • npm
  • pnpm
  • yarn
  • bun
npm install @credo-ts/tenants@alpha
pnpm add @credo-ts/tenants@alpha
yarn add @credo-ts/tenants@alpha
bun add @credo-ts/tenants@alpha

Configure​

agent.ts
import { AskarModule, AskarMultiWalletDatabaseScheme } from '@credo-ts/askar'
import { Agent, CacheModule, InMemoryLruCache } from '@credo-ts/core'
import { DrizzleStorageModule } from '@credo-ts/drizzle-storage'
import { tenantsBundle } from '@credo-ts/drizzle-storage/tenants'
import { agentDependencies } from '@credo-ts/node'
import { TenantInactiveError, TenantStatus, TenantsModule } from '@credo-ts/tenants'
import { NativeAskar } from '@openwallet-foundation/askar-nodejs'
import { drizzle } from 'drizzle-orm/libsql'

// Run the migrations of the core and tenants bundles first
const database = drizzle('file:agent.db')

const agent = new Agent({
  dependencies: agentDependencies,
  modules: {
    // The records of all tenants in one database
    storage: new DrizzleStorageModule({ database, bundles: [tenantsBundle] }),
    askar: new AskarModule({
      askar: NativeAskar,
      enableStorage: false,
      store: { id: 'credo-keys', key: 'my-agent-store-key' },
      // The keys of all tenants in one Askar store, with a profile per tenant
      multiWalletDatabaseScheme: AskarMultiWalletDatabaseScheme.ProfilePerWallet,
    }),
    tenants: new TenantsModule({ sessionLimit: 100, sessionAcquireTimeout: 5000 }),
    // The default cache throws as soon as a second agent context (a tenant) uses it
    cache: new CacheModule({ cache: new InMemoryLruCache({ limit: 5000 }) }),
  },
})

The example stores the records of all tenants in one Drizzle database and their keys in one Askar store. Add tenantsBundle to bundles, pass --bundle tenants when you run the migrations, and use PostgreSQL in production.

Replace the default cache: it throws as soon as a tenant uses it. Use InMemoryLruCache, or RedisCache when several instances run the agent. See Caching.

TenantsModule optionDescription
sessionLimitMaximum number of tenant sessions open at the same time. Default 100, which is low on purpose: set it based on your hardware and load. Infinity removes the limit.
sessionAcquireTimeoutHow long, in milliseconds, opening a session waits for a free slot when the limit is reached, before it throws Failed to acquire an agent context session. Default 1000.

Tenant agents get the modules you register on the root agent. To type them, pass the modules to the generic, for example new TenantsModule<{ openid4vc: OpenId4VcModule }>().

Where tenant data is stored​

With Drizzle, all tenants share the one database, and each row is tagged with its tenant. Tenant keys are in Askar, where multiWalletDatabaseScheme decides where they go. Set it to AskarMultiWalletDatabaseScheme.ProfilePerWallet, as in the example: all tenants in one Askar store, with a profile each.

With Askar storage​

When Askar also stores the records, multiWalletDatabaseScheme decides where all tenant data goes:

multiWalletDatabaseSchemeTenant records and keys
ProfilePerWalletA profile per tenant in the root store
DatabasePerWallet (default)A store per tenant, a SQLite file or a PostgreSQL database each, with a generated key that Credo saves in the tenant record

Use ProfilePerWallet. It keeps all tenants in one database, performs better with many tenants, and doesn't create a PostgreSQL database per tenant. Store-level tasks, such as rotating the store key or exporting the store, then cover all tenants at once. DatabasePerWallet is the default for backwards compatibility: use it only to back up or delete tenants one by one.

No SQLite path with DatabasePerWallet

Tenant stores reuse the root store's database config. With an explicit SQLite path, all tenants resolve to the root store's file, and createTenant fails. Leave path unset so each tenant gets its own file in the data directory.

Create a tenant​

agent.ts
const tenantRecord = await agent.modules.tenants.createTenant({
  config: { label: 'Tenant 1' },
})

createTenant saves a TenantRecord in the root agent's storage and creates the tenant's storage. The label is for your own use. Use the tenant record's id to open the tenant later.

Use a tenant​

Work in a tenant through a tenant agent, which has the same API as the root agent, scoped to the tenant. withTenantAgent opens a session, runs your callback and ends the session, also when the callback throws:

agent.ts
// Opens a session, runs the callback and always ends the session
const did = await agent.modules.tenants.withTenantAgent({ tenantId: tenantRecord.id }, async (tenantAgent) => {
  const { didState } = await tenantAgent.dids.create({
    method: 'key',
    options: { createKey: { type: { kty: 'OKP', crv: 'Ed25519' } } },
  })
  return didState.did
})

getTenantAgent returns the tenant agent without a callback. End the session yourself with endSession():

agent.ts
const tenantAgent = await agent.modules.tenants.getTenantAgent({ tenantId: tenantRecord.id })
try {
  const createdDids = await tenantAgent.dids.getCreatedDids()
  console.log(`Tenant has ${createdDids.length} DID(s)`)
} finally {
  // Every session counts against the session limit until you end it
  await tenantAgent.endSession()
}

Each open session takes a slot of sessionLimit until it ends, so a missing endSession() eventually blocks new sessions. Inbound DIDComm messages and OpenID4VC requests for a tenant open their own session.

Manage tenants​

agent.modules.tenants has methods to look up and change tenants:

MethodWhat it does
getTenantById(tenantId), findTenantsByLabel(label), findTenantsByQuery(query), getAllTenants()Find tenant records.
updateTenant(tenantRecord)Saves changes to a tenant record.
updateTenantStatus(tenantId, status)Activates or deactivates a tenant. See Tenant status.
deleteTenantById(tenantId)Deletes the tenant record and the tenant's storage.
getTenantsWithOutdatedStorage(), updateTenantStorage({ tenantId })Update tenant storage after a Credo upgrade. With autoUpdateStorageOnStartup, Credo updates a tenant when it opens a session.
agent.ts
await agent.modules.tenants.deleteTenantById(tenantRecord.id)

Tenant status​

A tenant is active or inactive. New sessions can't be opened for an inactive tenant: withTenantAgent and getTenantAgent throw a TenantInactiveError, and inbound DIDComm messages and OpenID4VC requests for the tenant fail. Sessions that are already open keep working. Pass allowInactive: true to open a session anyway, for example for administration:

agent.ts
await agent.modules.tenants.updateTenantStatus(tenantRecord.id, TenantStatus.Inactive)

try {
  await agent.modules.tenants.withTenantAgent({ tenantId: tenantRecord.id }, async () => {})
} catch (error) {
  if (!(error instanceof TenantInactiveError)) throw error
  console.log(`Tenant ${error.tenantId} is inactive`)
}

// Admin tasks can still open a session for an inactive tenant
await agent.modules.tenants.withTenantAgent({ tenantId: tenantRecord.id, allowInactive: true }, async (tenantAgent) => {
  console.log(`Inactive tenant still has ${(await tenantAgent.dids.getCreatedDids()).length} DID(s)`)
})

New tenants, and tenants created before the status existed, are active. With Drizzle, the status is a column that the 0001_add-tenant-status migration of the tenants bundle adds.

Route messages and requests to tenants​

Tenants share the root agent's endpoints, and Credo finds the tenant for each incoming message or request:

  • DIDComm: when a tenant creates routing keys, for example for a connection, Credo saves which tenant they belong to, and it routes each encrypted message by its recipient key. See DIDComm.
  • OpenID4VC: create issuers and verifiers with a tenant agent. Credo routes requests to their URLs to that tenant. See Issuing credentials and Verifying credentials.
