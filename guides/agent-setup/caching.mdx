Credo caches data that is slow to fetch: resolved DID documents, AnonCreds objects from ledgers and revocation lists of X.509 certificates. A cache is always registered. This page covers what's cached, which cache to use, and when you have to replace the default, which is always the case with [multi-tenancy](./multi-tenancy.mdx).

## What is cached

| Data | Cached for | Scope |
| --- | --- | --- |
| Resolved DID documents, for methods whose resolver allows caching (`did:web`, `did:webvh`, `did:cheqd`, `did:indy`, `did:sov`, `did:hedera`). `did:key`, `did:jwk` and `did:peer` aren't cached. | 5 minutes, change it with `cacheDurationInSeconds` when resolving | Global for methods in `DidsModule({ publicDidMethods })`, otherwise per agent context |
| AnonCreds schemas, credential definitions, revocation registry definitions and status lists | 5 minutes | Global |
| Summaries of X.509 certificate revocation lists | Until the list's next update | Global |
| Indy VDR: which ledger a DID is on | Until evicted | Global |
| DIDComm connection, mediation and mediator routing records, with `useCachedStorageService: true` | Until evicted | Per agent context |

Entries in the global scope are public data that all [tenants](./multi-tenancy.mdx) share. `publicDidMethods` defaults to `web`, `indy`, `sov`, `cheqd`, `hedera` and `webvh`.

## Choose a cache

The default is `SingleContextStorageLruCache` with a limit of 500 entries. It keeps the entries in memory and saves them as a record in the agent's storage, so they survive a restart. It only works with one agent context: as soon as a tenant uses it, it throws `SingleContextStorageLruCache can not be used with multiple agent context instances`.

| Cache | Package | Tenants | Several processes share it | Survives a restart |
| --- | --- | --- | --- | --- |
| `SingleContextStorageLruCache` (default) | `@credo-ts/core` | No | No | Yes |
| `InMemoryLruCache` | `@credo-ts/core` | Yes | No | No |
| `RedisCache` | `@credo-ts/redis-cache` | Yes | Yes | Yes |

Keep the default for a single agent, such as a mobile wallet. Use `InMemoryLruCache` for multi-tenancy in one process, and `RedisCache` when several instances of the agent run behind a load balancer.

## Configure the cache

Register a `CacheModule` under the key `cache` to replace the default:

```ts showLineNumbers title="agent.ts" caching.ts section-1
```

`InMemoryLruCache` removes the least recently used entries when it reaches `limit`. The limit applies to all agent contexts together.

| `CacheModule` option | Description |
| --- | --- |
| `cache` | The cache to use. Required. |
| `defaultExpiryInSeconds` | Expiry for entries set without one. `RedisCache` uses it. Default `60`. |
| `useCachedStorageService` | Also caches DIDComm connection, mediation and mediator routing records, to save storage reads on busy DIDComm agents such as mediators. Default `false`. Only use it with a cache that all instances share, such as Redis, or with a single instance. |

`RedisCache` takes an `ioredis` client or `ioredis` options. Keys are prefixed with the agent context, or with `global:` for the global scope, so tenants and instances can share one Redis database. When you create the client yourself, close it after the agent shuts down:

```ts showLineNumbers title="agent.ts" caching-redis.ts section-2
```

`cache.destroy(agentContext)` removes all entries of one agent context, for example after you delete a tenant.
