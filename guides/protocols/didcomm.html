DIDComm

DIDComm is a messaging protocol for agents that keep a long-lived, encrypted connection with each other. Once two agents are connected, either side can start a protocol over that connection: issue a credential, request a proof, or send a message. Credo implements DIDComm v1 and the Aries RFCs built on it in @credo-ts/didcomm. This page explains when to use DIDComm and how to set up the module.

When to use DIDComm​

Use DIDComm when the parties have an ongoing relationship, because the connection stays usable after the first exchange. It is also the only protocol Credo supports for AnonCreds credentials, and the one other Aries-based agents use.

For one-off issuance or verification, and for wallets built for the EU Digital Identity Wallet ecosystem, use OpenID4VC instead. An agent can register both modules.

DIDCommOpenID4VC
RelationshipA connection that either side can use at any timeOne exchange per offer or request
Credential formatsAnonCreds, W3C VCsSD-JWT VC, mdoc, W3C VCs
Mobile walletNeeds a mediator to receive messagesCalls the issuer and verifier over HTTPS

Use DID Exchange and the 2.0 protocols. The deprecated protocols are removed in Credo 0.8, so only use them for agents that support nothing else. Credo doesn't implement DIDComm v2.

Configure the module​

Register a DidCommModule under the key didcomm. Credo only exposes the API as agent.didcomm under that key. Under any other key it is available as agent.modules.<key>.

  • Node.js
  • React Native

A server agent listens for incoming messages and advertises the URLs where other agents reach it.

agent.ts
import { AskarModule } from '@credo-ts/askar'
import { Agent } from '@credo-ts/core'
import {
  DidCommConnectionEventTypes,
  type DidCommConnectionStateChangedEvent,
  DidCommDidExchangeState,
  DidCommHttpOutboundTransport,
  DidCommModule,
  DidCommWsOutboundTransport,
} from '@credo-ts/didcomm'
import { DrizzleStorageModule } from '@credo-ts/drizzle-storage'
import { didcommBundle } from '@credo-ts/drizzle-storage/didcomm'
import { agentDependencies, DidCommHttpInboundTransport, DidCommWsInboundTransport } from '@credo-ts/node'
import { NativeAskar } from '@openwallet-foundation/askar-nodejs'
import { drizzle } from 'drizzle-orm/libsql'

const agent = new Agent({
  dependencies: agentDependencies,
  modules: {
    // Drizzle stores the records. Run its migrations before you start the agent.
    storage: new DrizzleStorageModule({ database: drizzle('file:agent.db'), bundles: [didcommBundle] }),
    // Askar stores the keys: DIDComm needs its XSalsa20-Poly1305 support
    askar: new AskarModule({
      askar: NativeAskar,
      enableStorage: false,
      store: { id: 'acme-agent-keys', key: 'acme-agent-store-key' },
    }),
    didcomm: new DidCommModule({
      // The public URLs other agents use to reach this agent, in order of preference
      endpoints: ['http://localhost:4040', 'ws://localhost:4041'],
      transports: {
        inbound: [new DidCommHttpInboundTransport({ port: 4040 }), new DidCommWsInboundTransport({ port: 4041 })],
        outbound: [new DidCommHttpOutboundTransport(), new DidCommWsOutboundTransport()],
      },
      connections: { autoAcceptConnections: true },
    }),
  },
})

await agent.initialize()

A mobile agent has no public address, so it only sends messages and receives them through a mediator.

agent.ts
import { AskarModule } from '@credo-ts/askar'
import { Agent } from '@credo-ts/core'
import {
  DidCommHttpOutboundTransport,
  DidCommMediatorPickupStrategy,
  DidCommModule,
  DidCommWsOutboundTransport,
} from '@credo-ts/didcomm'
import { agentDependencies } from '@credo-ts/react-native'
import { NativeAskar } from '@openwallet-foundation/askar-react-native'

// The invitation URL your mediator hands out
const mediatorInvitationUrl = 'https://mediator.example.com/invite?oob=eyJ...'

const agent = new Agent({
  dependencies: agentDependencies,
  modules: {
    askar: new AskarModule({
      askar: NativeAskar,
      store: { id: 'wallet', key: 'wallet-key' },
    }),
    didcomm: new DidCommModule({
      // No endpoints and no inbound transports: messages reach the wallet through the mediator
      transports: {
        outbound: [new DidCommWsOutboundTransport(), new DidCommHttpOutboundTransport()],
      },
      mediationRecipient: {
        mediatorInvitationUrl,
        mediatorPickupStrategy: DidCommMediatorPickupStrategy.PickUpV2LiveMode,
      },
      // A wallet doesn't act as a mediator
      mediator: false,
    }),
  },
})

await agent.initialize()

The Node.js example stores records with Drizzle, which also explains the packages and migrations it needs, and keys with Askar. DIDComm needs Askar, or another key management backend with XSalsa20-Poly1305, for its keys. See Storage for the options.

Endpoints and transports​

endpoints lists the public URLs that go into your invitations and DID documents, in order of preference. Behind a reverse proxy, use the public URL (for example https://agent.example.com/didcomm), not the local port. An agent without endpoints can only receive messages through a mediator, or over a WebSocket it opened itself.

TransportPackagePlatforms
DidCommHttpOutboundTransport@credo-ts/didcommNode.js, React Native
DidCommWsOutboundTransport@credo-ts/didcommNode.js, React Native
DidCommHttpInboundTransport@credo-ts/nodeNode.js
DidCommWsInboundTransport@credo-ts/nodeNode.js

DidCommHttpInboundTransport takes a port and an optional path. Pass app instead of port to mount it on an Express app you start yourself. DidCommWsInboundTransport takes a port, or a server (a WebSocketServer from ws). To serve HTTP and WebSocket on one port, give the WebSocket server noServer: true and forward the HTTP server's upgrade events to it, as the sample mediator does.

Protocols​

The connection, out-of-band and discover features protocols are always on. The other protocols are on by default. Pass false to turn one off, which also removes its API from agent.didcomm, or pass an object to configure it.

OptionConfiguresDetails
connectionsConnections and DID ExchangeConnections
credentialsIssue Credential 2.0Issuing credentials
proofsPresent Proof 2.0Requesting proofs
mediatorActing as a mediatorMediation
mediationRecipientUsing a mediatorMediation
messagePickupPickup 1.0 and 2.0Mediation
basicMessagesBasic messagesMessaging
warning

By default, credentials and proofs register the 2.0 protocols without any credential formats, so the agent can't issue or verify anything. Configure the formats you need as described in Issuing credentials and Requesting proofs.

Events​

Credo emits an event for every state change, such as a connection being completed or a message arriving. Listen with agent.events.on(), and remove the listener with agent.events.off(). agent.events.observable() returns the same events as an RxJS observable.

agent.ts
agent.events.on<DidCommConnectionStateChangedEvent>(
  DidCommConnectionEventTypes.DidCommConnectionStateChanged,
  ({ payload }) => {
    const { connectionRecord, previousState } = payload
    console.log(`Connection ${connectionRecord.id}: ${previousState} -> ${connectionRecord.state}`)

    if (connectionRecord.state === DidCommDidExchangeState.Completed) {
      console.log(`Connected with ${connectionRecord.theirLabel}`)
    }
  }
)

The event type enums and payload types are exported from @credo-ts/didcomm.

Event typePayload
DidCommConnectionEventTypes.DidCommConnectionStateChangedconnectionRecord, previousState
DidCommOutOfBandEventTypes.OutOfBandStateChangedoutOfBandRecord, previousState
DidCommCredentialEventTypes.DidCommCredentialStateChangedcredentialExchangeRecord, previousState
DidCommProofEventTypes.ProofStateChangedproofRecord, previousState
DidCommBasicMessageEventTypes.DidCommBasicMessageStateChangedbasicMessageRecord, message
DidCommRoutingEventTypes.MediationStateChangedmediationRecord, previousState

Each event also has metadata.contextCorrelationId, which tells you which tenant it belongs to when you use multi-tenancy.

Connections

Create and accept out-of-band invitations, connect agents with DID Exchange, reuse connections and track connection state in Credo.

Issuing credentials

Issue credentials over DIDComm with the Issue Credential v2 protocol, register credential formats and handle offers, requests and auto-accept.

Requesting proofs

Request and verify presentations over DIDComm with the Present Proof v2 protocol, using AnonCreds or DIF Presentation Exchange.

Mediation

Run a DIDComm mediator with Credo and connect mobile agents to it, with message pickup, live delivery and keylist updates.

Messaging and other protocols

Send basic messages over a DIDComm connection, and add the action menu, question answer and DIDComm RPC protocols to a Credo agent.

AnonCreds with DIDComm

Issue AnonCreds credentials and request proofs with predicates over DIDComm, and handle revocation.

W3C VCs with DIDComm

Issue W3C Verifiable Credentials over DIDComm as JSON-LD, Data Integrity or VCDM 2.0 SD-JWT credentials, and present them with DIF Presentation Exchange.
