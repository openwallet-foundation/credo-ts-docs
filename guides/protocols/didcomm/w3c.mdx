---
title: W3C VCs with DIDComm
description: Issue W3C Verifiable Credentials over DIDComm as JSON-LD, Data Integrity or VCDM 2.0 SD-JWT credentials, and present them with DIF Presentation Exchange.
---

Credo issues W3C Verifiable Credentials over DIDComm with three credential formats, and presents VCDM 1.1 credentials with DIF Presentation Exchange. This page covers the options and limits of each format. The protocol flow itself is on [Issuing credentials](./issue-credential.mdx) and [Requesting proofs](./present-proof.mdx), and the credential model on [W3C Verifiable Credentials](../../credential-formats/w3c-vc.mdx).

## Formats

| Format key | Spec | Credential | Holder binding | Stored as | Present over DIDComm |
| --- | --- | --- | --- | --- | --- |
| `jsonld` | [RFC 0593](https://github.com/decentralized-identity/aries-rfcs/tree/main/features/0593-json-ld-cred-attach) | VCDM 1.1 with an Ed25519 Linked Data signature | DID in `credentialSubject.id` | `W3cCredentialRecord` | yes, as `ldp_vp` |
| `dataIntegrity` | [RFC 0809](https://github.com/decentralized-identity/aries-rfcs/tree/main/features/0809-w3c-data-integrity-credential-attachment) | VCDM 1.1 with a Linked Data signature, or VCDM 2.0 with a Data Integrity proof | signed nonce, AnonCreds link secret, or DID in `credentialSubject.id` | VCDM 1.1: `W3cCredentialRecord`, VCDM 2.0: `W3cV2CredentialRecord` | VCDM 1.1 only |
| `w3cV2SdJwt` | [RFC 0881](https://github.com/decentralized-identity/aries-rfcs/tree/main/features/0881-w3c-vc-sd-jwt-credential-attachment) | VCDM 2.0 secured with SD-JWT (`vc+sd-jwt`) | signed nonce, as `cnf` | `W3cV2CredentialRecord` | no |

`vc+sd-jwt` here is a W3C VCDM 2.0 credential secured with SD-JWT, not an IETF [SD-JWT VC](../../credential-formats/sd-jwt-vc.mdx) (`dc+sd-jwt`). There is no DIDComm format for SD-JWT VC, mdoc or VCDM 1.1 JWT credentials.

## JSON-LD credentials

:::issuer

```ts showLineNumbers title="issuer.ts" didcomm-w3c.ts section-2
```

:::

The holder accepts the offer without format options, and stores the credential as a `W3cCredentialRecord`.

- Credo signs with `Ed25519Signature2018` or `Ed25519Signature2020`, so the issuer needs an Ed25519 key. Each suite only accepts its own verification method type. A `did:key` has `Ed25519VerificationKey2018` methods, so use `Ed25519Signature2018`.
- Set `proofPurpose` to `assertionMethod`. The issuer signs with the first verification method of the issuer DID that fits the proof type. Pass `jsonld: { verificationMethod }` to `acceptRequest` to choose another.
- Every `@context` must resolve. Credo bundles common contexts, such as the VC data model, the security suites, Open Badges 3.0 and schema.org, and fetches others over the network. To add your own context, see [W3C Verifiable Credentials](../../credential-formats/w3c-vc.mdx).
- Don't add `credentialStatus`. Credo can't check W3C credential status, so the holder fails to verify such a credential.
- The holder proves control of the DID in `credentialSubject.id` when it presents the credential. To learn the holder's DID, let the holder [start with a proposal](./issue-credential.mdx#start-with-a-proposal) that contains it.

## Present VCDM 1.1 credentials

Present JSON-LD credentials, and VCDM 1.1 Data Integrity credentials, with the DIF Presentation Exchange format, as shown on [Requesting proofs](./present-proof.mdx). The holder signs an `ldp_vp` presentation with an `authentication` key of the DID in `credentialSubject.id`. VCDM 1.1 JWT credentials you received another way, such as with OpenID4VC, can be presented as `jwt_vp`.

## VCDM 2.0 SD-JWT credentials

The RFC 0881 format issues a VCDM 2.0 credential secured with SD-JWT, with selectively disclosable claims.

:::issuer

```ts showLineNumbers title="issuer.ts" didcomm-w3c.ts section-3
```

:::

- `credential` is a VCDM 2.0 credential without proof. You can leave out `issuer` and pass it to `acceptRequest` instead.
- `disclosureFrame` lists the claims the holder can disclose selectively. `@context`, `type`, `credentialStatus`, `credentialSchema` and `relatedResource` can't be selectively disclosable at the top level.
- With `bindingRequired` and `didCommSignedAttachmentBinding`, the holder must sign a nonce with a key of one of its DIDs. Restrict the accepted keys with `didMethodsSupported` and `algsSupported`. Without binding, the holder gets a bearer credential.

Auto-accept can't answer an offer that requires binding. The holder calls `acceptOffer` and picks the key:

:::holder

```ts showLineNumbers title="holder.ts" didcomm-w3c.ts section-4
```

:::

The issuer sets the holder's DID as `credentialSubject.id` and the key as `cnf`, signs the credential and sends it. With `ContentApproved` this happens automatically. Otherwise call `acceptRequest`, where you can also set `alg`, `issuerVerificationMethod`, `disclosureFrame` or `credentialSubjectId`. The holder verifies the credential, checks that it matches the offer and stores it as a `W3cV2CredentialRecord`.

Limits:

- The exchange always starts with an offer. Proposals and holder-initiated requests aren't supported.
- You can't present these credentials over DIDComm. Present them with [OpenID4VP](../openid4vc/w3c.mdx).

## Data Integrity credentials

The RFC 0809 format issues VCDM 1.1 and 2.0 credentials. The first `@context` entry decides the data model.

:::issuer

```ts showLineNumbers title="issuer.ts" didcomm-w3c.ts section-5
```

:::

- A VCDM 1.1 credential gets a Linked Data signature, as with the JSON-LD format. A VCDM 2.0 credential gets a Data Integrity proof. Credo registers one cryptosuite, `eddsa-jcs-2022` for Ed25519 keys, and you can name it with `cryptosuite` in `acceptRequest`.
- Binding with `didCommSignedAttachmentBinding` works as in the RFC 0881 format, but the issuer doesn't derive `credentialSubject.id` from it. Put the holder's DID in the offer, or pass `credentialSubjectId` to `acceptRequest`. Credo doesn't issue a bound credential without subject id automatically.
- For VCDM 2.0 credentials, Credo doesn't check the holder's binding proof. Put the holder's DID in `credentialSubject.id` instead.
- The `anonCredsLinkSecretBinding` option issues AnonCreds credentials in W3C format, see [AnonCreds with DIDComm](./anoncreds.mdx#anoncreds-in-w3c-format).

The holder stores VCDM 2.0 credentials as a `W3cV2CredentialRecord`, but the exchange record lists them with `credentialRecordType: 'w3c'`. Look them up with `agent.w3cV2Credentials.getById`.

Limits:

- The exchange always starts with an offer.
- VCDM 2.0 Data Integrity credentials can't be presented over DIDComm or OpenID4VC.
