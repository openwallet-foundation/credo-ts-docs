This page covers W3C Verifiable Credentials over OpenID4VC: which forms work, the credential configurations, signing in the credential mapper, DID binding, and requesting them with DCQL. [Issuing credentials](./issuer.mdx), [Receiving and presenting](./holder.mdx) and [Verifying credentials](./verifier.mdx) explain the flow itself, and [W3C Verifiable Credentials](../../credential-formats/w3c-vc.mdx) explains the formats.

## Supported forms

| Data model | Secured as | OpenID4VCI `format` | Issue and receive | Present with DCQL |
| --- | --- | --- | --- | --- |
| VCDM 1.1 | JWT | `jwt_vc_json` | Yes | Yes, `jwt_vc_json` |
| VCDM 2.0 | SD-JWT | `vc+sd-jwt` with `credential_definition` | Yes | Yes, `vc+sd-jwt` with `meta.type_values` |
| VCDM 1.1 | JSON-LD (Linked Data Proofs) | `ldp_vc` | Not recommended | No |
| VCDM 2.0 | JWT or Data Integrity | none | No | No |

[What doesn't work](#what-doesnt-work) explains the last two rows. The rest of this page uses the first two.

## Configure the credentials

```ts showLineNumbers title="issuer.ts" openid4vc-w3c.ts section-1
```

- `credential_definition.type` lists the credential types.
- `vc+sd-jwt` with a `credential_definition` and no `vct` is a W3C VCDM 2.0 credential. With a `vct` it's an [SD-JWT VC](./sd-jwt-vc.mdx).
- W3C credentials are bound to a DID of the holder, so list DID methods in `cryptographic_binding_methods_supported` (or `did` for any method). Credo doesn't bind W3C credentials to a bare key.
- Add a `scope` if you offer the credentials through the [authorization code flow](./authorization.mdx).

## Sign the credentials

The issuer signs with a DID that it created in its own agent, and the mapper puts the holder's DID in the credential:

```ts showLineNumbers title="issuer.ts" openid4vc-w3c.ts section-2
```

- `issuerDid` is a DID created with `agent.dids.create`, for example `did:key`. `verificationMethod` is the id of its signing key. W3C credentials can't be signed with an X.509 certificate. See [DIDs](../../dids-and-trust/index.mdx).
- `holderBinding.keys` has a `didUrl` for each holder key. Its DID becomes the credential subject.
- For VCDM 1.1 (`ClaimFormat.JwtVc`), return a `W3cCredential` and the verification method. Credo picks the JWT algorithm from the key.
- For VCDM 2.0 (`ClaimFormat.SdJwtW3cVc`), return a `W3cV2Credential`, the `alg`, the `holder` (written to `cnf`) and a `disclosureFrame`. `@context`, `type`, `credentialStatus`, `credentialSchema` and `relatedResource` can't be selectively disclosable at the top level.

## Receive and store

The holder needs a DID it controls, and the binding resolver returns its verification method:

```ts showLineNumbers title="holder.ts" openid4vc-w3c.ts section-3
```

VCDM 1.1 credentials arrive as a `W3cCredentialRecord`, which you store with `agent.w3cCredentials`. VCDM 2.0 credentials arrive as a `W3cV2CredentialRecord`, stored with `agent.w3cV2Credentials`. Credo verifies both before returning them. It accepts any DID issuer unless you configure trusted issuers, see [Trusted issuers](../../dids-and-trust/trust.mdx).

## Request with DCQL

```ts showLineNumbers title="verifier.ts" openid4vc-w3c.ts section-4
```

- `meta.type_values` lists alternative sets of types. Credo compares them with the `type` values as they appear in the credential, not with expanded JSON-LD IRIs.
- For `jwt_vc_json`, the wallet presents the whole credential.
- For `vc+sd-jwt`, the `meta.type_values` make it a W3C VCDM 2.0 query, and `claims` paths point into the credential, for example `['credentialSubject', 'degree']`. The wallet discloses only those claims.

## Read the presentations

```ts showLineNumbers title="verifier.ts" openid4vc-w3c.ts section-6
```

- A `jwt_vc_json` query gives a `W3cJwtVerifiablePresentation`, with the credentials in `verifiableCredential`.
- A `vc+sd-jwt` query gives a `W3cV2SdJwtVerifiablePresentation`. The credential is enveloped in it, and `resolvedCredential` has the disclosed claims.

## What doesn't work

- `ldp_vc` (JSON-LD credentials with Linked Data Proofs) has known problems in this version. A Credo holder only finds a proof algorithm if `proof_signing_alg_values_supported` also lists the proof suite name, such as `Ed25519Signature2018`. Signing a `W3cCredential` created with `new W3cCredential()` fails unless you set `id` and `expirationDate` (or create it with `W3cCredential.fromJson`). And presenting `ldp_vc` credentials with DCQL fails when Credo creates the presentation. Use `jwt_vc_json` or `vc+sd-jwt` instead.
- `jwt_vc_json-ld` is issued and stored like `jwt_vc_json`, but DCQL has no format for it.
- VCDM 2.0 credentials secured as a plain JWT (`vc+jwt`) or with Data Integrity proofs have no OpenID4VCI format, and DCQL can't present them.
- DIF Presentation Exchange only works with the OpenID4VP drafts, and not for VCDM 2.0 credentials.
- Credo doesn't check `credentialStatus` of W3C credentials. See [W3C Verifiable Credentials](../../credential-formats/w3c-vc.mdx).
